# Round 4 response shaping

All changes below are mobile-only; no shared web labels changed. Existing fields
remain. Authentication/owner/area policies remain those documented for each route.

- GET `/api/mobile/today`: `headerChips[].label` now says "$… left to collect on N
  open jobs", counting construction + closeout (the same population as the money
  value); `priorities[].sub` gets the safe notification copy pass.
- GET `/api/mobile/leads`: `summary` omits the repeated "Pipeline ·" and uses
  "in the pipeline" for the probability-weighted amount.
- GET `/api/mobile/notifications`: `title` and `subline` replace configuration/env
  details with plain service-attention sentences. No raw details are echoed even
  to owners (original records/server logs remain available). Subs tab and dated
  acknowledgment reminders use phone wording and human dates.
- GET `/api/mobile/settings`: `notifyToggles[].label` uses "Money: draws, invoices,
  payments", "Deadlines: insurance, licenses, taxes", "Mentions in team chat",
  "Daily email at 7 am". Keys/on values are unchanged.
- GET `/api/mobile/warranty`: adds `coverageSummary:string` and
  `coverageTermsSummary:string`. Phone should replace its locally constructed
  "N without terms" with these fields. Counts/coverage/claim records are unchanged;
  zero terms reads "None have terms recorded yet" without asserting coverage.
- GET `/api/mobile/calls/{id}`: `call.transcript:string|null` maps the caller channel
  (0 inbound, 1 outbound, based on the recorded leg in voice-flow) to contact
  name/Caller; the other channel is You for owner viewers, SJ Carpentry for staff. Other channels retain neutral numbered speaker labels.

GET `/api/mobile/approvals` now adds `approvals[].record.destination`:

```ts
type MobileDestination = {
 type:"project"|"lead"|"sub"|"vendor"|"thread"|"sms"|"call"|"chat"|"approval"|"web";
 id:string|null; slug:string|null; section:string|null; focus:string|null;
 view:string|null; key:string|null; href:string;
};
type ApprovalRecordAddition = {destination:MobileDestination|null};
```

No body; existing Approvals owner/Today gate applies. All other approval fields,
including contentHash and send/approval identity, are unchanged. Null destination
means no href. This matches queue/notification destination enrichment. Query-based
email IDs (thread/threadId), view, section/tab and focus survive; inbox tab calls,
texts/sms and chat route to their corresponding types. `section` takes precedence
if both section and tab are present. Original href always survives, including
unsupported sections, so clients can offer the exact web fallback. Phone routing
must consume these fields rather than reducing href to pathname.
