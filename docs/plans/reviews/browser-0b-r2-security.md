2. **Real faults and survivors: substantially fixed; final dispatch remains uncovered.** The fixture now SIGKILLs a separate controller, records PID/signal, detaches an actual session without explicit fallback revoke, and checks browser-namespace survivors before finally cleanup. The active-response test is now a genuinely retained transfer rather than a second request on a one-request transport. However, killing during consume and after response buffering does not test loss between the last successful controller RPC and first upstream HTTP bytes; see required fix 1.

## REQUIRED fixes

1. **P1 — Cover and fence controller loss at final request dispatch; the documented window is not confined to responses.** `deploy/browser/transport_runtime.py:292`, `:537`, `:565`–`:577`; `deploy/browser/transport_control.py:152`–`:163`; `lib/browser/root-fixture.mjs:155`–`:162`; `docs/plans/build/browser-0b-root-acceptance-RESULT.md` (final controller-loss bullet).

   The last controller check is `server_connected`, before the upstream TLS handshake. After the handshake the runtime checks the decision clock/local handler, then sends headers and the frozen body without consulting controller liveness again. The lease can still be sleeping or awaiting its next reply. A hostile endpoint can hold TLS completion, let the controller die just after its successful RPC, and complete TLS before lease revocation. The gate can then start a previously buffered POST after controller death. Similarly, an ongoing upload can continue until detection. This is an already-consumed exact request, not an arbitrary unsigned request or a demonstrated authority forgery; nevertheless it contradicts the requested “no new request bytes” interpretation and the RESULT's response-only description of the window.

   **Offline repro performed:** extracted the actual `TransportHandler.run` AST into an in-memory Python harness (no source changes, imports of installed runtime, sockets or browser). Stubbed policy/TLS IO and flipped controller liveness at the existing `after_connect` fault point, leaving the local runtime live as it is before the next lease tick. Both real run-method calls to `server_tls.write` executed with controllerAlive=false: 55 HTTP bytes, including the complete `MUTATION` POST body. This establishes the unchecked control-flow path, not an independently observed root packet leak.

   **Exact change:** add a controller-confirmed, exact-flow/digest-bound final dispatch check after TLS establishment and immediately before releasing HTTP headers/body; make controller-lifetime loss actively cancel pending dispatch and upload IO rather than relying solely on the periodic response lease. Preserve consumed writes as unknown/no-retry. Add deterministic loss tests with the hostile TLS peer held after `server_connected`, and with an upload held between TLS records; actually kill the controller and release the peer immediately, without waiting for `controller_lost`. Assert no not-yet-dispatched request starts, bounded socket/process cleanup, and durable unknown. Repeat these with root ingress evidence before claiming this boundary closed. The immediate-reader active-response variant should also measure the detection/drain interval instead of hiding it with the current wait.

   Already-queued kernel bytes cannot be recalled, and the plan explicitly allows an already-dispatched consumed request to be unknown. A bounded drain of an already-authorized response is acceptable under that distinction; a new buffered request starting during the same window must not silently inherit that exception. Document the precise dispatch linearization point and unavoidable already-queued/in-flight bytes. If the intended contract instead permits an already-consumed but not-yet-dispatched mutation to start after death, obtain an explicit plan change and describe that broader guarantee; the present response-only caveat is insufficient. An extra RPC alone cannot establish a literal zero-time race-free physical-death guarantee.

## Assessment of the other acceptance changes

- **Browser-level popup:** acceptable. A distinct later paused page target still needs its own attach/guard/resume/Fetch/write chain. Generic parent traffic cannot substitute for the exact child digest.
- **OOPIF navigation on parent:** acceptable for the initial document fetch before the frame process exists. Parent guard/consume/write ordering is checked and the exact child.example digest reaches the origin; the new child must then attach paused and guard before resume. `--site-per-process` makes the separate frame-target claim meaningful. A post-attach child subresource regression would strengthen coverage beyond this initial-navigation case.
- **Detach ack OR boot_revoked:** acceptable as evidence of fail-closed termination following the actual attempted detach, together with unknown/no-write and no-survivor checks. It is weaker evidence of *which handler* caused termination: any subsequent boot revocation qualifies. Optionally record the target/session detach event or fixed detach reason to make mutation sensitivity and causal attribution explicit.
- **Review hold inside two seconds:** acceptable. It respects the existing dispatch deadline and does not extend signed authorization. Human review remains before dispatch. The RSS case retains its simultaneous frozen request/response and controlled-tail measurements.
- **Control backlog 2 to 8:** acceptable. This adds bounded Unix pending connections, not body slots. Socket mode 0600, root peer authentication, bounded framing and serialized dispatch remain. An untrusted browser cannot submit those control messages. A trusted root peer can still stall/control the runtime, but already has stronger powers; malformed or failed control fails closed. No new context, digest-confusion or unbounded-body allocation path was found in this change.
- **Shutdown codes:** acceptable. Failure remains failure, and independent kill is attempted even when revoke/fence fails. Terminal persistence failures remain sticky and cannot yield a durable successful revoke acknowledgment.
