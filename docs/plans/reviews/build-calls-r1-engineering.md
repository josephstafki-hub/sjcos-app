## Defects

1. **High — phone completion is blocked.** `components/calls/checklist/ChecklistPane.tsx:377` puts Finish inside the scroll container with a sticky bottom of zero, without accounting for shell bottom UI. The coordinator's actual production-side phone run found Finish covered and unclickable. This is a reported functional failure, not my own visual reproduction; the precise covering element still needs coordinator inspection. Phase 1 cannot pass while its primary completion action is inaccessible.

2. **High — recovered edits can be silently deleted before the recovery decision.** `components/calls/checklist/useChecklistSync.ts:184` loads stored edits into `recovered`, separately from `state.queue`; `:87` persists only the latter and removes the session entry when it empties. At `:223`/`:233`, normal row/notes edits remain enabled while recovered edits await Send now/Discard. Reopen online with three pending edits, tick another row, let it acknowledge, then reload without choosing: the new edit overwrites the persisted three, and acknowledgement removes the entry. The recovered edits existed only in React memory and are lost. This directly breaks reload recovery acceptance.

3. **High — account isolation is advisory at send time, and logout cleanup is incomplete.** `components/calls/checklist/useChecklistSync.ts:121` permits sending when the localStorage identity is absent; `:199` ignores its removal. `components/calls/checklist/signed-in.ts:8` returns null when storage is denied. `lib/actions/discovery-checklist.ts:14` mints authority for whichever user owns the current cookie, without comparing the queued edit's original user. With localStorage unavailable, leave A's offline tab open, sign in as B (also with comms), then reconnect A's tab: A's queue can be submitted as B. Separately, switching users leaves the old snapshot/recovered values on screen. Cleanup exists only in Sidebar's fire-and-forget submit handler (`components/shell/Sidebar.tsx:335`), not `/logout` (`app/logout/route.ts:12`) or expiry paths; those leave recoverable PII behind. Partitioned IDB helper tests do not cover these cases.

4. **Medium — expected errors are thrown across the production server-action boundary.** `lib/actions/discovery-checklist.ts:20`, `:129` and `:143` let SQL/domain errors escape; the result type in `lib/checklist-coverage/manual.ts:11` represents only success or conflict. `components/calls/checklist/useChecklistSync.ts:159`/`:173` and `ChecklistSummary.tsx:106` branch on thrown CHECKLIST messages. Production Next replaces those messages, so invalid-answer, operation-reused, missing-email and version-conflict handling becomes generic. The UI builder's concern is correct. Conflict-as-data already works; all expected failures need that same treatment, without exposing SQL details. The classifier unit test merely acknowledges generic production errors; it does not repair their loss.

5. **High — dial success can be lost, enabling a second real call.** `lib/actions/discovery-checklist.ts:98` reads the revision, awaits `placeCallAction`, then at `:101` ignores a possible conflict result from linking. Tick the checklist on another device while dialing: the call succeeds, linking returns 409, and the session still has no call ID. Retrying the same start operation reaches `placeCallAction` again. The advisory lock serializes starts but does not prevent normal edits. There is also no durable recovery between successful dialing and linking after a process failure. Separately, `components/calls/CallsClient.tsx:135` creates a fresh operation ID on every manual-start retry; a committed start with a lost response produces a second session.

6. **High — follow-up conflict retry can silently change the client recipient.** `components/calls/checklist/ChecklistSummary.tsx:95` automatically reloads a new revision and retries staging the same body after a conflict, without refreshing/reconfirming the displayed To. `lib/actions/discovery-checklist.ts:142` derives To from the session's then-linked lead. If another device relinks Alex's checklist to Blair before submission, Alex's displayed draft/body can be staged to Blair after the automatic retry. Approval still prevents an immediate send, but the wrong-client PII has entered a ready-for-approval draft. Lead email changes are also outside the session revision. The operation hash does not bind the recipient, so identical draft retries can conceal target changes. The server should read lead identity under the session lock rather than using the pretransaction snapshot at `:128`.

7. **Medium — link-later skips the insurance notice task.** `db/migrations/0074_discovery_checklist.sql:431` creates the deduplicated notice only during set_item when a lead is already linked; `:437` simply updates the link. Start the intended unlinked checklist, enter insurance, then link the lead and finish: no notice task is created. The call warning appears, but §3.2 requires the lead/initial-estimate task too. Relinking an insurance checklist has the same omission for the new lead.

8. **Medium — acceptance tests stop below the failing integration boundaries.** `tests/checklist-offline.test.mjs:4` tests one pure recovery filter; `tests/checklist-offline-store.test.mjs:88` clears a closed fake DB, not actual logout while a hook is active. `tests/checklist-access-db.test.mjs:70` exercises the staging primitive, not `stageChecklistFollowup`'s replay/transaction boundary. There are no new tests exercising the authenticated action/route/MCP checklist path end-to-end, hook recovery-plus-new-edit, production-safe error results, dial/link races, or recipient changes. The database-role paths test passes but does not specifically exercise the newly registered checklist tools. Passing the named files therefore falls short of the plan's behavioral acceptance evidence.
