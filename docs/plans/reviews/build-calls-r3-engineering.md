It can omit a just-created lead during that minute, but cannot alone explain an omission several minutes later. Define recent as creation/contact recency, add stable ordering, and invalidate/revalidate prefetch after creation; preserve caller-first ordering. The lost-stage filter is intentional, not a width-dependent filter.

### New GET route: auth, side effects and cost

`app/api/calls/checklist-leads/route.ts:12–18` resolves the current principal, rejects signed-out users with 401 and users without Calls access with 403 before searching, and sets `Cache-Control: private, no-store`. `lib/dal.ts:50–52` rejects inactive/revoked principals; `:70–74` allows owners and only staff with `comms`, denying portal roles. An inline transpiled-handler probe with real `can` and stubbed principal/search boundaries passed anonymous, denied staff, portal, owner and Calls-staff cases; only the two authorized cases reached search. This is not an end-to-end session-cookie test. No CORS opt-in or public caching was added. The remaining data-minimization issue is listed above.

The helper runs only SELECTs; GET does not create a checklist, change contact dates or stage drafts. CSRF is not required for this read-only operation. Queries use bound parameters, truncate text to 80 characters and return at most 12 results after merging caller matches. Cost is one search query plus an optional caller-phone query, not N+1. However, LIMIT bounds output, not work: leading-wildcard ILIKE, normalized-phone regex and last-contact sorting can scan/sort leads; only the ordinary stage index is evident (`db/schema.sql:1193`). Acceptable for a small internal list, with no measured production latency claim; evaluate query plans and normalized-phone/search indexes if lead volume warrants it. No live DB was queried.
