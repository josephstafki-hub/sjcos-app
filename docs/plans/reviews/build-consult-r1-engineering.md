## Defects

1. **P1 — sensitive UI state survives authorization loss and lease expiry.** `lib/consult/ui/controller.ts:393–402` silently returns on a snapshot 403 and merely sets a code on 401; `:236–241` publishes decrypted state before its asynchronous drain; `:462` clears `local` and thumbnails but retains `fresh`, `draft` and boot data. There is no expiry timer protecting `getState()`/`snapshot()` rendering. A prepared tab with no pending ops can reconnect after its assignment was revoked, receive 403 from refresh and remain in `phase: visit` with the previous private snapshot and photo URLs. A disconnected tab left open past expiry also retains its rendered data even though the engine correctly refuses its next read/capture. A direct controller reproduction of refresh returning 403 retained `local`, `fresh`, thumbnails and visit phase. Apply denial/expiry to the whole presentation state and all decrypted references, preserve ciphertext, and revalidate before exposing cached data on reconnect (§12.1).

2. **P1 — takeover bypasses the missing-device safeguard; recovery is not reachable.** `lib/consult/protocol.ts:105–117` revokes every device on assignment without an old close manifest or explicit missing-device exception. `:283` computes close devices from only unrevoked rows. Harness reproduction: save answers/evidence, assign the same visitor again, start a replacement device, Close with `last_seq:0` → **`complete:true`**, while the old revoked device's `close_manifest` is NULL. The real device could still hold unsent work unknown to the server. Requiring one active device (`:350–360`) correctly matches §5.4; silently dropping the former device's closing obligation does not. `AssignControl` in `components/consult/office/ScheduleDialog.tsx:94–104` only changes the visitor and disables same-visitor Save. No consult UI calls `recovery_lease` or `recover_device`; no explicit owner Set aside/takeover flow collects a reason or preserves a missing-work completion gate. The second-browser refusal therefore has no safe same-visitor UI remedy.

3. **P1 — offline Close is neither durable nor automatically resumed.** `lib/consult/ui/controller.ts:407–434` stores Close only in in-memory `state.closing`; offline execution sets `waiting_signal` and returns without persisting intent/evidence/manifest. `:360–390` drains answers/uploads on reconnect but never retries Close. `components/consult/field/ConsultApp.tsx:128–129` wires Send now to drain only. Reproduction: offline Close yields `waiting_signal`; a new controller has `closing:null`. The visitor can leave believing the visit is closed/sending, then lose that action on reload or reconnect and never reach server Complete. Persist an exact close intent with the encrypted visit and resume it after preceding receipts, retaining idempotency through lost acknowledgments (§5.5, §12.2).

4. **P1 — retained builds break cold offline navigation.** `public/sw.js:36–39` reads `consult_build` only from `event.clientId`'s existing client, ignoring the navigation request URL. Cold navigation may have an empty clientId; with two retained build caches, candidates becomes empty even for `/consult/<id>?consult_build=old`. A VM execution of the actual worker with two ready caches, empty clientId, that explicit query and disconnected fetch returned **503**. This defeats the handoff's documented old-build recovery path. Select navigation build from the requested URL, and keep subordinate assets pinned to the selected client build. Cover cold navigation with multiple complete caches and an interrupted/incomplete new cache.

5. **P1 — Get ready accepts PINs the vault refuses, then traps retry.** `components/consult/field/GetReady.tsx:55–62` accepts 4–8 digits and truncates to eight; `lib/consult/offline.ts:89` requires 6–12. Four/five-digit PINs pass the UI after all readiness work, reserve the device and fail enrollment. `lib/consult/ui/words.ts:244–251` calls both `invalid_pin` and `device_access_denied` a sign-in failure. `GetReady.tsx:104–106` then offers only Try again with the same saved PIN, with no correction form in that state. Agree on one policy across enrollment/unlock/Hand back/copy, show the actual error, and let the visitor correct the PIN. Validate before reserving a device when possible.

6. **P1 — migrations cannot install without precreated narrow roles.** `db/migrations/0077_consult_files.sql:17` fails on its direct multi-role REVOKE; `:65` also creates a policy naming absent roles, and other REVOKEs repeat the problem. `0078_consult_jobs.sql:9` has the same unconditional role reference. Independently reproduced by starting a brand-new harness cluster and calling `loadSchema` without `ensureDbRoles`: **`0077_consult_files.sql failed: role "sjcos_agent" does not exist`**. The ordinary tests create those roles first and mask this. Audit **all 0075–0079**, but do not blindly add grants: 0075 already guards role-specific revokes/grants; 0076 has PUBLIC-only revokes; 0079 introduces no new role-dependent grants. Use the repo's `sjcos_grant` helper for actual grants and equivalent existence-guarded revokes/policy construction in 0077/0078. Do not grant raw consult content merely to make installation pass. Test both bootstrap orders, including later provisioning of roles/RLS policy.

7. **P2 — recovery manifest rejects real committed media receipts.** `lib/consult/protocol.ts:372` validates `blobs[].receipt.file_id` as UUID; `lib/consult/uploads.ts:83` creates file IDs as `consult-${uid}`. Passing the engine's own recovery manifest after any media commit therefore fails Zod validation before staging otherwise recoverable pending answers. Validate the actual file ID format, recheck its consult ownership, and round-trip a mixed pending/synced-media manifest in the recovery test. The current recovery test has no blobs and misses this.
