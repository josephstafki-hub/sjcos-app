## New defects

1. **N1 — P2: unknown thrown send errors are still called “no signal”; tests do not establish the requested general protection.** `lib/consult/offline-engine.ts:49` recognizes only `TypeError('Illegal invocation')`; every other thrown value becomes `no_signal`. Direct replay reproductions returned `no_signal` for both `Error('unexpected adapter bug')` and a thrown string; `Illegal invocation` correctly returned `transport_invocation`. The receiver wrapper at `:13–16` is correct and the coordinator's real browser success is accepted. But `lib/consult/ui/controller.ts:47–48` also classifies **every TypeError** as a network failure, including upload/refresh programming errors. The UI suppresses normal failure treatment for `no_signal` (`components/consult/field/ConsultApp.tsx:23,56,109–111`). Its later stuck fallback mitigates silence; it does not preserve the true diagnostic or prove that any thrown error is handled honestly. `tests/consult-send.test.mjs:10–48` makes receiver misuse throw only if the wrapper regresses, then tests successful delivery; it does not inject arbitrary exceptions or assert failure presentation. Use a shared, conservative network classifier and a visible non-network/unknown transport failure, retaining diagnostics. Cover answer and upload exceptions, non-Error throws, malformed responses, and real network failures.

2. **N2 — P2: stuck/failure timing does not match the claimed behavior.** `components/consult/field/ConsultApp.tsx:41–47` starts `waitingFrom` whenever work exists, even offline; it never resets on an online transition. Answers waiting offline for ten minutes become “stuck” immediately upon reconnect, rather than after two minutes online. Conversely, `:110–111,158` delays the synthetic failure's action banner for another minute after the two-minute threshold: the status changes at two minutes, the banner at three. For explicit failures, retries reset `lastSendFailure.at` (`lib/consult/offline-engine.ts:41–43`), and the UI always prefers those errors over the stable stuck time. Retries occur every 2–60 seconds (`lib/consult/queue.ts:61–77`; controller `:419–424`), so repeated failures can keep resetting the one-minute action-banner delay indefinitely. The status/detail failure remains visible; the promised persistent action banner is what fails. Track the start of the continuous online/no-progress failure separately from the latest attempt. Show the stuck banner at its actual threshold. `tests/consult-r2-design.test.mjs:67–74` only matches source names and cannot detect these timing defects; add clock-controlled behavioral cases for offline/reconnect, repeated retries and progress resetting the clock.

3. **N3 — P2: a room name alone still becomes “Looked over” in the client acknowledgment.** `lib/consult/ui/model.ts:366–375` counts every answered field, including the identifying `name`, as covered work and falls back to “Looked over” when it finds no measurements or mapped choices. Direct `summaryInput` reproduction with just Room 1's name answered produced `rooms:[{name:'Room 1 — Kitchen',work:['Looked over']}]` and an empty `come_back`. No inspection or measurement was recorded. This defeats the round-2 truthfulness fix for a common first action in a room. Exclude identifying/preset-only fields from substantive coverage; keep such rooms in “We'll come back to …” until actual work is recorded. The existing summary test covers a completely untouched room and a measured room, missing this middle case. The grouping, kitchen-wall exclusion, five-item truncation and summary allowlist otherwise look sound.

4. **N4 — P2: a final Close failure can wait indefinitely without an automatic retry.** With all operations/media acknowledged, `resumeClose` catches a failed Close POST and retains the durable request (`lib/consult/ui/controller.ts:450–477`). `drain` schedules its next attempt only from pending answer entries (`:419–421`). An in-memory controller reproduction with GET success, `navigator.onLine=true`, an empty queue and a Close POST throwing `TypeError('Failed to fetch')` ended with `closing:{step:'waiting_signal',code:'no_signal'}`, `online:true`, durable intent retained, and **`timer:null`**. Recovering the connection without a browser online event does nothing until another user action/reload; losing the final acknowledgment has the same scheduling problem. Retry retained Close intent with bounded backoff independently of pending answers, using the persisted exact request, and stop retrying on actionable/non-transient failures. Add a cold-reload and lost-ack regression that confirms automatic retry and one server effect. This is why round-1 item 3 remains partial, despite its substantial fix.

Round-2 seed help→note separation is accepted: field and shot types/validators support `hint` and internal `note`; `components/consult/field/FieldRow.tsx:111,215` renders only hints. `tests/consult-hints.test.mjs` checks actual seed hints for plan/scope markers and the renderer for note/help exposure; all three tests pass.
