## New defects

### N5 — P1: required-instance initialization is interruptible and never reconciled on resume (missing Closing)

The pin itself is present, but a pin is a definition, not an instance. Scheduling stores pins/assignment without creating visible instances (`db/migrations/0075_in_home_consults.sql:249–274`; schedule options include all published modules at `lib/consult/ui/server.ts:90–101`). Current Bath and Kitchen templates both require Closing (`lib/consult/forms/seed/templates.ts:88,105`), and the OR merge preserves `required:true` (`lib/consult/template-merge.ts:9–12`). An in-memory run with the actual seed produced Closing slot `{required:true, minimum:1, live:0}` and an uninterrupted real controller `start()` created exactly one Closing. **The current merge does not drop Closing.**

The verified lifecycle gap is `lib/consult/ui/controller.ts:318–345`: Start is durably committed first, then instances/presets are written sequentially. Closing follows 30 merged Bath+Kitchen selection presets, each requiring create and answer writes. The UI regards the visit as started as soon as the start entry exists (`lib/consult/ui/model.ts:352`; `components/consult/field/ConsultApp.tsx:159–168`), before initialization finishes. Reload, navigation, storage failure or interrupted initialization can therefore leave a started visit without Closing. Unlock only restores/drains (`controller.ts:243–252`); it never reconciles required instances. The other reconciliation trigger is only `rooms_wanted` (`:354`). The section list then renders the missing required slot as Add closing (`components/consult/field/VisitScreen.tsx:57,75–78`).

Reproduction: inject an interruption immediately before the Closing commit during actual controller Start. Durable state has `started:true`, zero Closing instances, Closing still required with minimum 1, and last save `Decision`. This reproduces the reported state without changing pins. The exact interruption/timing in the coordinator's run is not established: the current source also permits observing this transiently during initialization. Do not claim a proven OR-merge regression or silently alter immutable pins to fix it.

**Required fix/test:** make initialization resumable and idempotent from durable state, and give initialization an explicit busy/error state until its required base instances exist. For a freshly scheduled Bath+Kitchen visit, use published/pinned definitions, prepare and Start through the controller, then assert one Closing instance, its four required price-critical fields, and an accessible promised-date action. Inject interruption during selection defaults/before Closing, cold-unlock and resume; assert Closing is created exactly once, existing answers/presets survive, and a second resume creates no duplicates. Include offline initialization and the coordinator's exact published pin set if it differs from the seed. Preserve server enforcement of the required Closing module.

### N6 — P2: area deduplication removes genuinely unmeasured rooms from the acknowledgment

`lib/consult/ui/model.ts:466–468` removes a room from Not measured today whenever any covered section has the same display area, even when that section has no measurements. In-memory reproduction with an untouched `room` labelled `Room 1 — Bath` and only `bath_scope.existing_tub_material = 'Cast iron'` returns a Bathroom entry and **`come_back:[]`**. Neither room dimension was captured. The new wording/deduplication in `a8a15b67` therefore hides the very measurement gap that list claims to disclose. Merging solely by display heading (`:462–463`) also collapses distinct unnamed rooms for the same area.

**Required fix/test:** track substantive scope coverage separately from measurement coverage and room identity. A bathroom may have been discussed while remaining unmeasured. Keep that fact visible, with wording that supports both truths. Add cases for a material-only scope answer plus an untouched room, two rooms sharing an area with only one measured, and the existing name-only/measured-room cases. A scope answer or another room's dimensions must not erase the untouched room.

### N7 — P2: photo-only transient failure still has no automatic retry

The new Close timer fixes final Close, but `lib/consult/ui/controller.ts:424–428` schedules ordinary drain retries only from pending answer entries. An upload-only replay exception (`lib/consult/offline-engine.ts:43,61–70`) leaves the blob durable without creating an answer retry entry. With accepted answers, one outstanding photo, browser `navigator.onLine=true`, and replay throwing `TypeError('Failed to fetch')`, a controller reproduction ends with `online:false`, `timer:null`, retained photo and `no_signal`. A brief request failure while the browser remains connected produces no online transition to resume sending. Manual Send now/reload can recover; automatic transport recovery cannot. This is a newly uncovered existing gap, not evidence that the new Close retry failed.

**Required fix/test:** schedule bounded retries for outstanding upload work independently of answer entries, stopping for actionable authorization/permanent failures. Exercise a real upload-only engine/controller path: accepted answers, queued photo, transient initialization/part/commit failure, restored transport without browser event, then automatic delivery and one committed media effect. Check the pending-photo count and Last sent after success, plus authorization-loss cleanup.
