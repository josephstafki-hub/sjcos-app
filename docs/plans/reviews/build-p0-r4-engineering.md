## Coordinator findings

### Expiry: a separate background action can navigate the whole app

The Ask action POST itself no longer redirects in Proxy. `proxy.ts:166–169` takes POST + `Next-Action` through stamped `next(req)`, and the actual exported Ask actions return their typed failure. In `useAgentChat`, `askCall` throws the fixed result into `reportFailure`; that path does not call `settle`/queue refresh after a rejected send.

**There is nevertheless a deterministic redirect source alongside Send.** The persistent layout mounts `LiveUpdates`, which calls `pollLiveChanges` every 2.5 seconds (`components/shell/LiveUpdates.tsx:47`, `:73`). `lib/actions/live.ts:10` calls the redirecting `requireUser()`. Fresh execution using the real DAL returns `NEXT_REDIRECT;push;/login;307;` with a missing session, while Ask actions under the same session return `SIGN_IN_AGAIN`. A second automatic read, `refreshTodayQueue` (`lib/actions/today.ts:127`), produces the same digest; the provider calls it on window focus (`components/today/TodayQueueContext.tsx:189–193`). Replacing a cookie via another window can coincide with precisely that focus path.

The installed Next action handler converts an escaping redirect into `x-action-redirect` (`node_modules/next/dist/server/app-render/action-handler.js:803–815`). The installed action reducer navigates for that header (`node_modules/next/dist/client/components/router-reducer/reducers/server-action-reducer.js:215–253`). The client poller's catch cannot prevent this framework navigation. `pollNotificationCenter` is a useful contrasting control: it already returns null for a missing current user rather than redirecting.

**A separate RSC GET also still redirects**, as intended for protected page navigation: the fresh Proxy check with `RSC: 1` and an expired cookie receives 307 `/login`. `LiveUpdates` can issue such a GET through its queued `router.refresh()` even after a failed poll, because its refresh block is outside the catch (`:58–69`). Installed `use-router` documentation explicitly says refresh makes a new server request. Passing all unauthenticated RSC requests through Proxy would not fix the lifecycle correctly; protected pages still enforce DAL authentication, and this would broaden the change unnecessarily.

No QA request log/action ID was supplied, so I cannot claim which individual request won the race in that browser run. The automatically issued live-poll action and focus queue action are independently reproduced redirect sources; no RSC refresh is necessary for them to explain the whole-window outcome. This is **not the intended in-panel expired-session behavior**. Round 3 deliberately retained redirects for real page navigations, not for background reads that displace the mounted chat.

### Journal directory permissions: safe denial, insufficient diagnosis

Fresh disposable SQL/filesystem execution reproduces the setup failure. With a bootstrapped never-enabled installation and no authority, Ask admits normally. Changing only its journal directory to 0775 makes every request pause with zero callbacks. At this HEAD the directory check throws **`JOURNAL_PERMISSIONS`** (`lib/canvas-deletion-ledger.mjs:34`); `JOURNAL_BINDING` is used by other binding/file checks. The outer journal catch collapses this to stored `JOURNAL_UNAVAILABLE` (`lib/ask-thread-journal.mjs:133`). Actual owner status returns only `{ok:true,status:"paused",code:"ASK_PAUSED",capabilities:{deleteAvailable:false}}`, HTTP 503/no-store. The repair item reports generic `RECOVERY_FAILED`, not permissions (`app/api/internal/canvas-maintenance/route.ts:24`). Thus neither owner-facing operational surface tells ops why it paused. Staff status correctly refuses access.

`docs/plans/build/phase0-B-HANDOFF.md:364` already specifies an owner-only 0700 journal volume. It does **not** explain that recursive `mkdir({mode:0700})` leaves an existing directory's mode unchanged, recommend letting the app create the leaf directory, or give a safe permissions repair procedure. Correcting the disposable directory to 0700 reopened the permitted never-enabled state without deleting evidence.

## Optional / recorded limitations

- Availability caches are single module slots keyed by a local numeric generation, not principal or a map of generation promises. Fresh independent tab realms cannot poison each other. Within one document, a new consumer at the same generation can reuse a failed/previous-consumer result; alternating generation 0 → 1 → 0 creates three requests. Successful panel Retry increments generation and recovers correctly. Consider an explicit principal/session epoch plus keyed in-flight requests if same-document account switching or independently recovering multiple panel consumers is introduced. Full-page sign-in naturally reloads the module. This is capability-boolean freshness, not a private transcript disclosure.
- Migrate the two older Telegram test fixtures to explicit owned/ready disposable chats and current privacy expectations. The ownerless-chat denial and private-reply exclusion are intentional; do not make production code satisfy their old assertions.
- Retain independently backed protected-volume/bootstrap and restore-drill evidence as deployment requirements. The client/SQL fixtures do not establish deployed authority durability or actual backup failure-domain separation.
