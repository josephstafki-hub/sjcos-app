REQUIRED fixes

1. **High — restore the device registry privilege boundary.** Backend `db/migrations/0092_phone_push.sql:60` and `deploy/db-roles.manifest.json:2149`. The migration grants agent/worker INSERT and unrestricted UPDATE of push_devices, and even gives the monitor SELECT of full tokens. An agent can insert its own device token with Joe's user_id (or replace Joe's token) and receive every owner alert, including client text and draft details. This directly reverses the previous deliberate withholding of this secret table. Remove narrow INSERT and ownership/token mutation grants and monitor token reads. Keep registration owner-website-only; expose only the minimum delivery read/disable operations to actual senders through restricted columns or purpose-specific functions. Update manifest and migration together, including REVOKE for installations that already applied these grants. Test that narrow roles cannot attach a token to an owner or change a destination.

2. **Medium — prevent cross-user token takeover.** Backend `app/api/mobile/push/[...path]/route.ts:20`. Any active staff bearer that knows an owner's token can re-register it, changing its user_id and clearing revocation. Owner pushes then stop for that device. This does not by itself send owner alerts to the staff phone: APNs still targets the supplied token and the owner-role delivery filter excludes its new staff owner. Nevertheless it allows unauthorized reassignment and denial of owner alerts. Reject a conflict owned by a different user unless a verified device-transfer flow authorizes it; support legitimate shared-phone switching with a device-bound transfer credential or an explicit prior unregister. Add owner-token/staff-token collision tests.

3. **High — revoke push delivery with the session/device authorization.** Backend `lib/phone-push.ts:19`; phone `src/lib/push/unregister.ts:8`. HTTP auth correctly rejects revoked sessions, but delivery checks only the user's active owner role and device flags. Revoking Joe's sessions leaves a lost phone receiving sensitive alerts indefinitely. Offline logout also swallows DELETE failure and forgets the token, with no durable unregister retry. Bind device registrations to an authorization generation and exclude registrations predating session revocation (fresh authenticated registration may renew them); preserve/retry unregister intent and clear delivered notifications on logout. Test a revoked-but-still-active owner and offline logout. Do not claim API revocation also revokes push until this is implemented.

4. **Medium — require authentication for typed notification actions too.** Phone `src/lib/push/categories.ts:35` and `:51`. Changes and Reply omit isAuthenticationRequired, although changes decides/pulls a request and reply can publish directly into a client portal. Approve/Decline/Hold set it. Set it on every mutating action, including both text actions, and assert it for every category in the tests. Foreground launch is already enabled and normally entails unlocking; this finding is the missing explicit action-authentication requirement, not a demonstrated iOS unlock bypass. If the product requires a fresh Face ID challenge for in-app decisions as well, add that gate to the shared action submission path; current in-app confirmation dialogs are not biometric authentication.

5. **High — honor hidden notification previews.** Phone `src/lib/push/native.ts:60`. All categories set showTitle:true. Installed Expo maps that to UNNotificationCategoryOptions.hiddenPreviewsShowTitle (`node_modules/expo-notifications/ios/ExpoNotifications/Notifications/TriggerRecords.swift:329`). Backend titles contain client names, project context, approval subjects and sometimes financial details, so they remain visible even when Joe hides previews. Remove showTitle:true (and do not enable showSubtitle), retain generic placeholders, and verify on a locked device with previews disabled. Plain body/title text is otherwise intentionally the same sensitive content Telegram receives; Telegram's per-device preview settings were not available to inspect.

6. **High — recover claimed actions and post-commit effects instead of abandoning them.** Backend `app/api/mobile/push/[...path]/route.ts:41`, `:43`; `lib/owner-actions.ts:114`, `:149`. A crash after INSERT push_actions but before execution permanently returns recorded with no action; a crash after approval commits but before performApprovalEffects leaves an approved card without its invoice/release/staged-send completion. The phone removes this response from its outbox (`src/lib/push/provider.tsx:292`). A portal post can commit before its note/ack/result is saved, leaving the owner unable to tell whether retrying with a new UUID will duplicate it. The recorded response is honestly ok:false, but does not meet completion/replay parity. Persist action state and domain mutation together where possible, queue durable effects with stable idempotency keys, and reconcile unknown provider outcomes rather than blindly resending. Retrying the same UUID must recover or expose a durable terminal/needs-review result with effect evidence. Add fault-injection coverage before mutation, after mutation, and after provider acceptance.

7. **High — put in-app answers through the durable outbox, and fail closed on persistence errors.** Phone `src/lib/push/provider.tsx:465`, `src/components/alerts/use-alert-actions.tsx:68`, `src/lib/push/store.ts:45`. Only notification responses are queued. In-app replies POST directly; after a lost response, the toast's retry reuses the UUID, but pressing Send again or relaunching generates a new one and can post the same client reply twice. Also store.save silently catches a failed disk write and permits sending, losing even notification-response deduplication on restart. Use one persistent submission path for all actions, save the UUID and exact request before networking, retain it through uncertain outcomes and relaunch, and report/refuse a send if persistence fails. Use atomic durable replacement rather than risking a truncated JSON file; test storage failure and restart after a timeout.

8. **High — scope pending answers to their author.** Phone `src/lib/push/outbox-core.ts:14`, `src/lib/push/provider.tsx:288`, `src/lib/push/unregister.ts:22`. Outbox entries contain no user/session identity, logout does not clear or quarantine them, and any subsequent owner login flushes them with its current bearer. Owner B can therefore publish owner A's queued portal reply as B or execute A's pending approval. Bind entries to the originating user and authorization generation, guard asynchronous flush completion against account changes, and explicitly discard/quarantine on logout or revocation; never silently adopt another user's pending actions. Test A logout → B login and a response arriving during an account switch.

9. **High — return actions on revised cards inside a thread.** Backend `lib/phone-push.ts:55`, `lib/notify-owner.ts:426`; phone `src/lib/push/feed.ts:18` and `src/components/alerts/alert-thread.tsx:159`. A revised draft intentionally has reply_to_id pointing to Joe's note and state=open. shapePushMessage refuses approval actions whenever reply_to_id exists, so it returns only reply. The phone lifts/render these revised cards expecting their server-supplied buttons, but Approve/Decline/Hold are missing. Distinguish actual actionable revision cards from conversational replies by kind/category and live approval state, not parenthood. Return appropriate actions for revised work-item and grant/decision cards; test real backend-shaped revisions in both feed and thread.

10. **High — reconcile live approval state, including failed-send reopening.** Backend `db/migrations/0092_phone_push.sql:50` and `lib/phone-push.ts:43`. claimApproval flips a draft to approved and the trigger marks its alert decided. If sending fails, reopenApprovalAfterFailedSend (`lib/approved-draft-send.ts:282`) returns the item to requested, but the trigger never reopens the alert and /open never reads current work-item state. Joe sees an approved/decided card with no retry button while the draft is unsent and awaiting him. Derive/reconcile card state against the current approval generation and outcome, restore the current card on a failed-send reopening, and keep obsolete revisions closed. Include expired decisions and already-resolved records inserted after the status trigger ran in reconciliation. Test failed-send reopening and stale parked cards against the phone's allowedActions and badge.

These are pure helpers/fixtures, not native authentication or actual backend-envelope integration tests. No server, browser, simulator, database cluster, build or typecheck was started; no cluster needs stopping. No source edits, staging or commits.
- Auth: all push endpoints call getUserFromRequest, which verifies JWT, active user, current database role and session revocation. Alert reads, actions, settings, open and test are owner-only; devices accept owner/staff and DELETE is user-scoped. push.saveSettings is ownerOnly and dispatch enforces that flag. Same actionId with a different user, message, verb or text returns 409. Contract docs should list 409 alongside the other error statuses; phone ApiError already handles it as final.
- Secrets at rest: no session JWT is serialized in push-state.json. The bearer is in SecureStore with AFTER_FIRST_UNLOCK, explicitly chosen for existing background geofencing. push-state.json contains device token, titles and typed client/agent replies in Documents; no explicit file protection class or backup exclusion is set by this code. Specify and verify the protection/backup policy on-device; prefer Complete protection or an appropriately protected encrypted store for foreground-only pending replies. Do not describe sandboxing alone as proof of locked-device confidentiality.
- APNs: .p8 is read from a server-configured path, provider JWT is ES256 and cached for 50 minutes; fake delivery records only token suffixes. APNS_API_BASE is an unrestricted server environment seam, not an HTTP input, so I found no staff/portal-triggered SSRF route. Harden production by forbidding overrides outside explicit test mode and never forwarding a real provider JWT to a non-Apple origin. Raw Error logging should be replaced with bounded/redacted transport errors, especially when using a test endpoint's arbitrary reason string.
- Injection: portal text is parameterized into SQL and rendered as native text; notification body is not parsed as a navigation destination. href/dest are separate structured fields. External HTTP(S) hrefs can still open through the alert's Open record action; constrain alert destinations to known internal routes or an explicit trusted-origin policy if agents may supply hrefs. I did not establish a portal-body-to-arbitrary-href injection path.
- Database trigger is correctly SECURITY DEFINER SET search_path = public, pg_temp. push_actions is intentionally withheld from narrow roles. These do not offset the push_devices grants in required fix 1.
