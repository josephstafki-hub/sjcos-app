## REQUIRED fixes

1. **High — fence action execution across lease expiry; one UUID currently posts twice.** Backend `app/api/mobile/push/[...path]/route.ts:38`, `:64`, `:68`; `lib/owner-actions.ts:115`, `:128`. The two-minute lease can expire while the original executor is still alive. Its replacement and the original both execute the portal INSERT; neither transaction verifies exclusive ownership before mutation. Completion also overwrites result unconditionally. **Reproduced against the actual endpoint:** lock chat_messages, launch a portal reply, wait until its INSERT blocks, advance its lease to expired, launch the identical UUID/request, wait until both INSERTs block, release the lock. Both responses are HTTP 200 / ok:true / posted, and two identical client-visible chat_messages rows exist. Advancing the timestamp simulates a database wait exceeding two minutes; it does not change execution code. **Exact change:** add a claim generation/fencing value, lock and verify the push_actions claim inside the same transaction before every domain mutation, and make evidence/completion updates conditional on the active generation and unset terminal result. Alternatively enforce a unique actionId on the domain mutation and recover its existing result. Ensure stale executors cannot perform effects or overwrite a terminal result. Add this overlapping-expired-lease regression for portal replies and owner notes, plus first-result stability coverage. A longer lease alone is insufficient.

2. **High — expired cleanup credentials must not silently leave delivery enabled.** Phone `src/lib/push/unregister-core.ts:27–32`; backend `lib/phone-push.ts:19–21`, `app/api/mobile/push/[...path]/route.ts:22`; JWT validation `lib/session.ts:40`. The phone treats every unregister 401 as proof delivery was revoked, deletes its pending intent and retained credential, and can say alerts are off. But a normal expired JWT also returns 401, while the registry stores only authAt and delivery never checks session expiration. Offline logout followed by expiry therefore leaves the signed-out phone receiving owner alerts indefinitely. **Reproduced:** register with a short-lived valid owner JWT, let it expire, DELETE returns 401, then token-targeted sendAppPayload still records one delivery. **Exact change:** persist the registering credential's authorization expiry and exclude expired registrations from fanout (renew on authenticated registration), or implement an independently revocable, device-scoped unregister credential that survives bearer expiry. Do not consume arbitrary 401s as confirmed removal unless the backend guarantees delivery has stopped. Test offline logout across expiry, foreground expiry, and subsequent account switching; assert both zero further delivery and truthful pending/off UI.

3. **High — implement Face ID for deciding/posting actions, including in-app actions.** Phone `src/lib/push/provider.tsx:499`, `:639–644`; `src/components/alerts/use-alert-actions.tsx:46–50`; `src/lib/push/outbox-core.ts:173`. No LocalAuthentication/authenticateAsync/biometric integration exists in src; in-app confirmation leads straight to enqueue and POST. Category isAuthenticationRequired requires device authentication for notification interaction; it does not provide a fresh Face ID check on an already-unlocked in-app action. Someone holding Joe's unlocked app can approve sends or post client replies. **Exact change:** add a shared native authentication gate for every newly authorized approve/decline/hold/changes/reply action before it becomes sendable, with Face ID configuration and fail-closed cancellation/unavailability handling. Bind the successful authorization to the exact request and session; retries may reuse that authorization only for that exact saved request. Route notification and in-app entry points through it. Test cancellation/no POST, all verbs, changed identity during authentication and replay of an already authorized queued request. Verify the native Face ID behavior on device.

4. **Medium — preserve informative titles in shown previews and outcome pushes.** Backend `lib/providers/apns.ts:22`; `lib/phone-push.ts:88` (notifyAppActionResult); `lib/notify-owner.ts:138`, `:574`. The generic title replacement drops m.title entirely, rather than moving it into the preview body. A title-only alert produces `{title:'SJC OS',body:''}`; this affects the folded “and N more” alert and the action-result row created with only a title. Payment/client context that exists only in title is also lost. **Reproduced directly through buildPushPayload** with a title-only completion message: empty body. **Exact change:** keep the generic APNs title but compose the visible body from the informative title plus optional body, deduplicating identical text and applying the existing UTF-8 size bound. Continue hiding both title/subtitle via category options. Test real completion, folded summary, portal, payment and contract payloads with previews shown, and verify hidden previews still show only generic placeholders.

## Additional security observations / optional items

- Route audit: getUserFromRequest gates every push route and verifies signed JWT, current active user/role and revocation. Devices allow owner/staff only; remaining routes require owner. Register cannot assign another user's userId; DELETE and test token selection are user-scoped. Messages are intentionally shared across authorized owners. push.saveSettings is ownerOnly and dispatch enforces it. Same actionId with a different user/request returns 409.
- Phone secrets: push state moved out of Documents into a chunked SecureStore journal using WHEN_UNLOCKED_THIS_DEVICE_ONLY; its atomic head is published after chunks. Legacy plaintext is migrated then deleted, including after a crash between commit/deletion. No bearer is written into that state. The normal session remains SecureStore AFTER_FIRST_UNLOCK for geofencing; retained unregister credentials use AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY. Actual keychain accessibility/backup behavior needs device verification.
- Injection/navigation: SQL parameters carry text, APNs uses JSON, and native text is not executed. Payload text is separate from destinations; slugs/ids are encoded into established routes. Notification taps with web-only destinations open the alert instead. Explicit Open record can still open arbitrary HTTP(S) hrefs via targets.ts; a trusted-origin policy is advisable for agent-supplied links. I did not establish a portal-text-to-arbitrary-destination path or automatic credential forwarding.
- APNS_API_BASE is server configuration, not an HTTP input. Production overrides are rejected; a real signing key cannot be used with a non-Apple origin. Transport errors now use bounded generic text/status instead of arbitrary Apple/test-endpoint reasons, and fake records expose only token suffixes. Route catch still logs raw error objects, which may include SQL row details; prefer structured error codes and correlation IDs there.
- SECURITY DEFINER helpers have fixed search_path. Narrow registry writes are closed. phone_push_reconcile retains PUBLIC execute by default; explicitly grant only intended callers as defense in depth.
