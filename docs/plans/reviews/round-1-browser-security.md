## Verified sound

Reviewed the browser plan at `abe0e023` against the requested source files. The shared branch advanced during review; the governing context now includes Joe's decisions 5–6 in `a30a530b`. Those decisions override the plan: named staff may use shared logins but never see their passwords, and Joe approves every company-committing final step. This is a plan review, not a claim that proposed controls already exist or passed runtime tests.

- **Vault foundation (§5.1):** AES-256-GCM, random 96-bit nonces, 128-bit tags, per-record data keys, identity/origin/revision AAD, separate encryption purposes, root-provisioned LoadCredential keys, CAS rotation, decrypt-only retention and separately encrypted escrow are sound choices. `lib/backup/crypto.ts:1–47` really does use age or AES-CBC/PBKDF2 for backups; the plan correctly declines to copy CBC into the vault. No key in application DB/backups/logs is the right boundary.
- **Model secrecy (§5.2, §8.2):** permanently private credential-bearing contexts, no page-derived private model observations, encrypted private downloads and guards on subsequent model file readers are substantially stronger than password-box masking. Buffer erasure limitations and the destination site's inherent knowledge of its own login are honestly described.
- **Shared-host isolation (§3.2):** a dedicated service UID and network namespace, namespace-only CDP, a narrow authenticated Unix socket, no public tunnel route, sandbox enabled, default-deny egress and a separate proxy are appropriate. Merely binding CDP to host loopback would not suffice. Deployment still needs actual negative tests from another local UID, not just configuration inspection.
- **SSRF coverage (§8.1):** the plan explicitly covers IPv4/IPv6 special ranges, mapped/embedded addresses, mixed DNS answers, rebinding, redirects, metadata, non-HTTPS schemes, the app's entire public host and aliases, and other local services. Rejecting resource origins as document or credential destinations is correct.
- **Authorization (§4, §6):** own-task staff access, `ai` plus task areas, owner review joining, per-device exclusive control, CSRF/Origin checks, stream reauthorization and revocation are appropriate. `lib/dal.ts:32–74` and `lib/api-auth.ts` actually read fresh user role/areas and revocations; `lib/permissions.ts` explicitly separates visibility from authority. React-cached DAL reads are correctly not proposed as the long-lived stream authorization cache.
- **Final actions (§7):** Enter, JS-driven requests, mutating GETs, autosave and manual staff payment are explicitly guarded; no arbitrary evaluate/CDP/model approval tool is proposed. Exact snapshots, expiring one-use tokens, transaction-bound grant consumption, immutable request manifests and unknown-result reconciliation address replay and ambiguous delivery well. `lib/owner-grant-types.ts:94–130` currently permits wildcard/optional-target grants, and `lib/owner-grants.ts:117–131` mints wildcard run grants; the proposed browser-specific rejection is necessary and correctly identified. `mcp/interact-mcp.mjs:54–72,107–151` autoallows classes of tools and persists permission inputs, so the separate browser approval channel is justified.
- **File and hosting precedents:** `lib/file-serve.ts` reads upload bytes and caches thumbnails; it only adds the sandbox CSP for HTML. The plan correctly requires private-file guards and a separate decrypt stream rather than reusing that helper unchanged. The checked-in nginx config has SSE support for MCP but no browser location; the tunnel routes to TLS nginx. The proposed browser SSE location needs no CDP exposure or WebSocket relay.
- **Database/attendance/recovery:** the manifest really has four narrow roles, backup has broad read authority, and ordinary owner runs retain owner DB access. Proposed zero grants on browser tables, a fifth narrow service role, explicit web-only approval commands, ask_web admission, visible-presence expiry, no unattended browser, resource limits and no automatic ambiguous retry are appropriate. Heartbeats prove a connected authorized UI, not that a human is continuously looking at it; do not describe them as proof of human attention.

## Vulnerabilities / gaps

1. **Critical — delegated-password visibility contradicts Joe's overriding decision (§5.2, §6.4).** The plan expressly concedes that an allowed destination can show credentials to an authorized human, while the sharing sheet promises “They can sign in without seeing the password.” A staff member with arbitrary live viewing/take-over can use a site's reveal control or visit an account page that reflects the shared secret; hostile page JS can render it as ordinary text or an image. Permanent model privacy does not protect the human stream. Joe's new decision 5 says staff never see it. This cannot be solved by hiding the SJC OS password API or masking only a known input.

2. **High — manual secret entry has no unconditional privacy transition (§5.2, §6.1, §10.2).** The carefully ordered transition is specified for vault fill, but take-over in a public context allows arbitrary key/IME/pointer input and has a separate private-input route without a reliable rule for selecting it. A page can request an OTP/password in an ordinary text field, replace a focused element, or reveal already typed text. Detection after entry is too late for a concurrent public observation or pending frame. “Once a secret enters” is a required invariant, not an implementable detection algorithm.

3. **High — prompt injection can survive a profile upgrade (§4, §8.3).** `scripts/run-claude-agent.mjs:868–887,956` resumes `ai_conversations.claude_session_id` and incorporates `unseenTranscript`; `persistToConversation` stores the continuing session. The plan restricts tools while browsing and resets MCP configuration, but does not prevent the next ordinary owner turn from resuming browser-tainted history with Bash, owner DB access and the app environment (`:976–1005`). A malicious public page can plant instructions for that later privileged turn. Fresh tools do not make old model context trusted.

4. **High — “read” traffic is an unspecified exfiltration exception (§7.1, §8.1–8.3).** Exact origin plus method/anchored path/field names does not constrain values. An allowed image/read endpoint can receive secrets or SJC OS data in query values, path segments, headers or Referer without being a business mutation. A hostile private page can send an encoded password to a second approved resource origin; a public injection can cause permitted model fills to leak business data through a nominally noncommitting adapter. A site allowlist and owner-only final steps are not a data-release policy. The destination-login exception does not authorize arbitrary secondary recipients.

5. **High — network enforcement claims exceed the specified mechanism (§3.2, §7.1, §8.1).** A CONNECT proxy with end-to-end TLS cannot inspect encrypted HTTP Host/authority, paths, methods or bodies as the plan implies. CDP interception performs those checks, but the independent proxy/firewall only enforces destination containment. If interception detaches or the controller fails while Chromium has an established allowed tunnel, a watchdog that subsequently closes the context is not proof that no intervening mutation leaves. The hard-stop guarantee needs a demonstrated fail-closed request gate, not just a post-failure cleanup promise. Per-context proxy credential isolation over the selected CDP runtime also remains an explicit unproven deployment dependency.

6. **High — session binding/expiry and authentication prerequisites are incomplete (§4, §6.1, §9.1–9.2, §10.2).** `lib/session.ts` has stateless JWTs with `authAt`, no session ID, a known development signing-key fallback, Bearer fallback in `readSession`, and logout merely deletes the cookie. The proposed table stores initiating_auth_at but no authenticated-session identity/expiry or viewer-session record; §9.2 refers to `sessions` without specifying a new session store. Rechecking a user and revocation timestamp cannot by itself prove that the originating browser session remains valid. The plan says cookie-only but needs an explicit cookie-only verifier, not accidental reuse of readSession's Bearer path. Same-user multiple devices and logout must have defined fencing behavior.

7. **High — narrow-agent DB fallback remains a bypass (§4, §9.2).** The plan expressly forbids owner fallback for the new browser DSN, but does not close it for the browser-profile SJC/interact subprocesses. `lib/db-login.mjs:74–91` resolves a missing narrow DSN to DATABASE_URL, including preferring an environment owner URL over a file narrow URL; `databaseUrlFor` discards the fallback indication. `deploy/db-roles.md` documents this behavior. Merely setting SJC_DB_LOGIN=agent does not guarantee the model's tools use sjcos_agent. A missing/misconfigured DSN can silently remove the SQL security boundary.

8. **Medium — envelope crypto is not fully specified for every private artifact (§5.1, §7.3, §8.2, §9.1).** Record encryption is specified, but the wrapping algorithm and canonical byte encoding/domain separation are not explicit. The listed AAD covers an entry/profile UUID and owner/origin/revision, while action bodies, review screenshots and saved files use envelopes too without their own normative identity binding. Rewrap must distinguish immutable data AAD from changing wrapping-key metadata. This leaves substitution and rotation behavior to implementer interpretation.

9. **Medium — append-only is not tamper-evident (§9.1, §9.3, §13).** browser_audit has no chained/authenticated digest or independent checkpoint. Restricting narrow writes helps, but the website/ordinary owner operator login owns the tables, as verified in the manifest and DB roles document. Rows can be edited, deleted or rolled back without detectable evidence. Existing owner-grant result logging is also best-effort (`lib/owner-grants.ts`, recordGrantResult); it must not become the only evidence of a browser dispatch.

10. **Medium — malware rejection is asserted, not a concrete file acceptance policy (§8.2, §12).** Magic checks, “reject malformed PDF,” and attachment disposition do not remove active PDF actions/embedded payloads or prevent a malicious valid PDF from being filed and opened by a person. The scanner is optional; the plan also says no automatic document parsing while promising PDF/polyglot/bomb validation. Image re-encoding and PDF validation themselves process hostile inputs and need bounded isolation. Existing file-serve's sharp thumbnail path is not such an isolation boundary.
