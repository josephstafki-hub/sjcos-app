Hash-only code, no eval, input rejection, namespace-aware reconstruction, and browser adversarial release tests are appropriate layers.
- Mermaid is isolated from the app DOM, with strict securityLevel, htmlLabels disabled, source config/style/click rejection and independently validated SVG exports. Upstream advisories confirm why these layers matter: [sequence-label XSS](https://github.com/mermaid-js/mermaid/security/advisories/GHSA-7rqq-prvp-x9jh), [state classDef injection](https://github.com/mermaid-js/mermaid/security/advisories/GHSA-ghcm-xqfw-q4vr), and [CSS injection](https://github.com/mermaid-js/mermaid/security/advisories/GHSA-6x64-9x62-f2gx). These are historical advisories, not evidence that the proposed 12.3.0 pin is vulnerable. The registry URL could not be fetched through the review's web tool; package integrity and the complete pinned dependency advisory check remain explicit implementation/release gates, as the plan requires.
- `AssistantMarkdown.tsx` escapes text and does not evaluate HTML/images. The plan preserves that boundary. `next.config.ts` supplies no application CSP; API routes must enforce their own policies. `lib/file-serve.ts` currently allows HTTP(S) images/fonts in HTML, and `/api/files/[id]` supports signature-only access. The plan explicitly replaces those behaviors for canvas-profile files, including portal, MCP, listing and attachment paths rather than assuming client_visible is sufficient.
- Download MIME/attachment/nosniff rules, static sanitized bytes outside the app, safe filenames, no server browser/PDF path, sandbox-preserving print wrapper, outer wrapper anti-framing, and release-gated Safari printing are sound. SVG decoding is restricted to validated derivatives with capped raster dimensions.
- Phase 0 correctly recognizes the real unscoped conversation queries in `lib/ai-chat.ts` and area-only actions in `lib/actions/ai-chat.ts`. Ownership before transcript/context assembly, run admission, attachments and mobile access is necessary. No narrow-role access to the new private tables is a good default.

Audit records avoid source/secrets. Tombstone-first deletion, purge holds, preserved saved-file provenance, backup aging/deletion replay, and security-compatible rollback are specified.

## Vulnerabilities / gaps

### High — a matching DB run is not proof the caller owns that run (§5.2)

The proposed adapter authenticates the shared CRON_SECRET and compares the supplied user/run/profile tuple with the DB. In the real MCP server, HTTP requests authenticated with MCP_HTTP_TOKEN can supply all those values through `x-sjc-principal-user`, `x-sjc-run-id`, and `x-sjc-run-profile` (`mcp/sjcos-mcp.mjs:3149–3153`). `principalPayload` forwards them and `internalCall` attaches CRON_SECRET (`:195–228`). An external/unattended caller claiming a real active panel tuple can satisfy every listed DB consistency check; checking interaction_surface on the victim run does not authenticate the calling transport. This does not require disclosure of CRON_SECRET to the model: the MCP process adds it. The proposed test that direct header impersonation is denied has no concrete enforcement mechanism. The plan's exclusion of compromised server administrators is reasonable, but should not turn every ordinary external MCP credential into a panel-run credential.

### High — sensitivity is captured only at creation (§9)

The conservative staff policy unions the creator's entire area set **at creation**, then says later versions may only expand. It never requires the server to add newly acquired areas on every update. Example: staff A creates with ai/projects, later receives money access, adds financial material to Version 2 without model labels, and saves it. Staff B with ai/projects can read the copy because the recorded set still lacks money. This defeats the stated protection against omitted model classification without violating any current plan rule. Current permissions really can change independently of sessions (`lib/dal.ts:32–85`). Restores, human version actions, and save-time policy handling also need consistent rules.

### Medium — owner sharing decision cannot be expressed in the normative Save API (§§8.4, 9)

§9 requires an explicit audited owner-only versus Share with staff decision and a required-area checklist. §8.4's strict request accepts only request_id, project_slug and filename. There is no audience field, alternative human action, or policy-binding/idempotency contract. Implementing the strict API leaves the approved sharing control ineffective; implementing the UI by accepting undocumented policy fields risks letting staff declassify files or reusing an already saved copy with an unintended audience. The active snapshot uniqueness is independent of audience, so policy mismatch on repeat Save must also be specified.

## Required to reach 10

1. **§§5.2, 8.1, 10 — authenticate panel transport provenance, not just tuple consistency.** For v1, explicitly refuse canvas calls on MCP HTTP transport regardless of claimed headers; only the per-run stdio registration may invoke the adapter, with a transport-derived discriminator that HTTP callers cannot select. Alternatively specify an unforgeable, expiring per-run capability verified by the adapter, bound to run/principal/thread/profile and revoked at run termination, never supplied in tool arguments or logs. Keep the existing DB/area/revocation checks. Add a test with a valid external MCP token and an exact real active owner/staff panel tuple; it must still fail, while the admitted run succeeds.
2. **§§5.1, 8.2, 8.4, 9, 10 — make conservative classification monotonic on every content write.** Atomically union stored requirements with the acting staff principal's current full area set and declared/derived scopes on every create/update/restore/latest action, not merely creation. Save must inherit the resulting server policy and may not drop restrictions; specify how later policy expansions affect existing copies (at minimum future saves must never return a weaker-policy copy). Add the ai/projects → add money → unlabeled update → save → less-privileged reader denial test, plus revocation and retry cases. Preserve owner-only defaults for owner content and explicit owner sharing as the sole declassification path.
3. **§§4, 8.4, 9, 10 — define the human audience contract.** Add a strict discriminated Save audience payload (owner_only versus staff with validated required_areas), default omission to owner_only for owner canvases, reject staff attempts to supply/weaken owner sharing policy, bind the effective policy to the idempotency hash and audit, and describe existing-copy policy mismatch behavior. Fail closed rather than silently widening an existing copy; test owner consent, staff forgery, same-key/different-policy retry, and same-version existing-copy audience conflicts.
