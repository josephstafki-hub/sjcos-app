## Sub agreements

### Verified correct

- The existing agreement upload slot is not a structured master/job agreement system; narrow logins have SELECT only on `sub_documents` (`lib/sub-doc-types.ts`; `deploy/db-roles.manifest.json:2701`). Receipt and owner acceptance must remain distinct.
- Existing e-sign is client/project/lead oriented. `TemplateScope` is project/lead/both (`lib/doc-templates/types.ts:103`); current signature requests have one signer (`db/schema.sql:1207`). The proposed audience separation and separate sub document types are necessary.
- `awardBidOp` exists (`lib/bidding.ts:814`), while `award_bid` is registered in procurement (`mcp/procurement-tools.mjs:237`; the old bidding module explicitly notes its move at line 843). Both low-level and commitment paths deserve attention.
- Client construction gates count signed contract/sow requests (`lib/procurement/gate.ts:26`). Calling a sub agreement `contract` would contaminate those gates; the plan correctly avoids this.
- Existing grant action/target are `send_document_for_signature` / `document_draft` (`lib/owner-grant-types.ts:13,38,49`). Reuse is appropriate; sending and authorizing extra work are separate authorities.

### Wrong or invented

- **Wrong existing tool contract:** §10, plan line 423, says `send_document_for_signature` takes `document_draft_id`. It takes numeric `draft_id`, `owner_grant_id`, optional `override` (`mcp/grants-tools.mjs:308–324`). Expected reviewed hash is a proposed extension. “Align … at implementation” leaves an explicitly requested contract unfinished.
- **Incomplete claimed execution model:** §9, lines 387–393, requires one request per signer, an execution packet, and `signature_packet` provenance without defining the packet entity/keys/state machine. Existing `document_drafts.signature_request_id` and its joins/send/void paths are singular (`lib/doc-drafts.ts:72,110,786,976–1028`). Merely adding two requests does not specify what that column means or which artifact is signed.
- **Overstated grant binding:** §5/§9 requires stale-content approval to fail, but existing `grantCovers` binds record target/recipient and exact email/SMS content, not a signature draft's hash (`lib/owner-grant-types.ts:112–155`). Content binding must be a real extension to the signature send operation, not an assumed feature.

### Required to reach 10

1. **§9 signing schema and §5 execution:** Define the packet table (or a fully specified alternative), signer-role uniqueness, request FKs, immutable unsigned content and attachment manifest, each signer's assent hash, executed artifact hash, completion/decline/void/supersession transitions, and recovery checkpoints. Explain how adding Joe's signature changes PDF bytes without invalidating the sub's assent. Replace every singular draft/request join, retry, void and client-portal assumption with explicit audience-aware behavior; name the hooks/readers to change. Add two-signer concurrency and crash-after-each-step assertions to `tests/sub-agreements-db.test.mjs`.
2. **§10 and §9 authorization:** Publish exact tool schemas, including `draft_id:number`, new optional/required hash fields, outputs and conflict codes; remove “align at implementation.” Define where approved hash/recipient is stored, checked and invalidated before consuming the grant/dispatching. Specify authenticated sub identity and assignment checks for every portal download/sign/upload and attachment, including signed download URL creation. Test swapped recipient, changed attachments and stale grants in `tests/sub-agreements-access-db.test.mjs`.
3. **§5 start gates and §9 constraints:** List the concrete tables, columns, transition names and operations for bid award, commitment approval, PO send, schedule confirmation and actual start. Specify which transitions warn versus block, initial adoption cutover, lock order, and the SECURITY DEFINER guard/function interfaces. There is no generic existing “schedule release” entity to implement against by inference. Provide composite job/sub/master/revision constraints, operative-term exclusion/supersession rule and indexes, plus a per-role/per-operation grant matrix rather than “only lifecycle operations it actually performs.”
4. **§11–12 operations:** Map the existing named tests and new tests to each phase, with acceptance cases for each bypass path. Add a named renewal/reconciliation worker or timer integration, lease/dedupe rules, delivery/render/completion failure visibility and repair ownership. Specify additive migration sequence, pilot/enforcement flags, rollback to warnings/manual release without invalidating signed records, and backfill verification counts. The adoption narrative is good; automated health and rollback are missing.
5. **§5 consult source adapter:** Replace the provisional “map … at implementation” contract (line 137) with the agreed `consultScopeFacts(projectId, scopeKey)` result schema, source version, verified/reviewed state, units, photo IDs and conflict rules. Keep manual confirmed facts available before consult Phase 4. Add the cross-plan fixture to `tests/consult-scope-facts-db.test.mjs` and the Work Order source tests.

## Discovery call

### Verified correct

- Raw signature verification and durable `source_events` persistence precede the response; `after()` handles immediate commands and the worker deferred work (`app/api/voice/webhook/route.ts:18–29,72–77`; `lib/worker/telnyx-processor.ts`). Existing transcript processing is post-call (`lib/voice.ts:381–408,517`).
- The nine existing `FACT_KEYS` and five canonical intake questions are correctly distinguished from the proposed five new fact keys (`lib/leads/qualification.ts`; `lib/lead-intake-questions.ts`). Worker writes to `lead_facts` need additional privileges (`deploy/db-roles.manifest.json:1312`).
- Native `transcription_start`/`transcription_stop`, `transcription_tracks:"both"`, `Telnyx`, and legacy A/B names are real. Track attribution is correctly a pilot condition, not guaranteed by dual-channel recording. [Telnyx command reference](https://developers.telnyx.com/api-reference/call-commands/transcription-start).
- Media streaming uses `both_tracks`, per-message inbound/outbound tracks and base64 headerless RTP payloads; separate STT streams are plausible. [Telnyx streaming guide](https://developers.telnyx.com/docs/voice/programmable-voice/media-streaming).
- Notes retry/idempotency concerns are real: `generateCallNotes` returns early on done, and knowledge capture uses content fingerprints (`lib/call-notes.ts:136,193–223`). Generic owner notifications and existing recording notice do not supply this plan's expiring nudges or affirmative consent sequence.

### Wrong or invented

- **Worker priority is not implemented by queue priority alone:** §6/§11 promises ≤250ms idle wake and bypass of slow recording jobs without specifying a scheduler change. Current worker processes claimed events sequentially, awaits the dispatcher, and allows a five-minute iteration (`lib/worker/loop.ts:95–130`; `lib/worker/types.ts:44–46`). An in-loop watchdog cannot run while that loop awaits slow notes generation.
- **The model “gateway” is a subprocess:** §5 describes remote inference through `chatReplyClaude`; this actually starts a fresh `claude -p` process per request, and defaults to the configurable chat model (`lib/dev-agents.ts:562–607`). Remote model execution is plausible; a 3-second end-to-end deadline, usage metering and “no new local model process” do not describe the CLI startup/resource overhead. The helper returns only text, discarding usage.
- **Native transcript normalization is still unpinned:** §6 names required track/timing properties without actual provider field paths or fixtures. The official example puts text/finality/confidence in `payload.transcription_data` and does not demonstrate a track identifier. Do not infer speaker from `call_leg_id` on a both-tracks canonical leg. This is an unresolved pilot dependency, not proof the command is invented. [Telnyx event example](https://developers.telnyx.com/docs/voice/programmable-voice/speech-to-text).
- **Offline reload is underspecified:** §4 promises refresh recovery of IndexedDB edits without an offline shell/service worker. Persisting edits survives refresh, but rendering Calls when the network is unavailable does not follow from persistence. This is particularly significant because the consult worker is scoped to `/consult/`.

### Required to reach 10

1. **§6/§11 scheduling and §13 tests:** Specify an independent bounded live scheduler inside the supervised process (or another explicit approved architecture), separate from awaited deferred jobs. Name changes to `scripts/sjcos-worker.mjs`, `lib/worker/loop.ts`, worker types and shutdown/heartbeat code. Define live ingestion priority before expensive processing, cross-process leases/fencing, wake cadence and backpressure. Add `tests/call-live-worker.test.mjs` proving a deliberately slow recording/notes job cannot delay consent-stop, live ingestion, watchdog or nudge expiry, and restart cannot double-process.
2. **§5/§6 provider and model adapters:** Supply exact native start/config/stop bodies and raw event-to-normalized fixtures, including missing track/time and corrections. Explicitly remain manual if speaker identity cannot be verified. For fallback, implement Telnyx WebSocket upgrade signature verification over timestamp plus exact stream URL, replay freshness and session binding; the current guide documents those headers, so generic “authenticate with a secret” is incomplete. Pin an explicit Sonnet model in the call, define a usage-returning CLI adapter or suitable persistent transport, measure startup-inclusive latency/concurrency and meter actual token/cost results. Test timeout kills and cost-cap races. Keep published rates provisional until account verification; no latency guarantee is established by the documentation.
3. **§5/§9 shared contract and security:** Publish a versioned exported input/output schema and adapter fixture used by both plans. Define durable mapping of consult bigint segment IDs to shared UUID segments, revisions, timing basis, unknown speakers and manual locks. Specify exact protected columns/functions for session consent, definition publication, evidence insertion and owner overrides, with function execution grants and record-scope checks. Generic table UPDATE plus application-only promises are insufficient for a narrow-login threat model. Add `tests/checklist-access-db.test.mjs` covering direct SQL attempts as agent/worker as well as MCP paths.
4. **§4/§7 manual persistence:** Choose either online reload with pending-edit recovery on reconnect (state that limit plainly) or an explicitly authenticated offline Calls shell. Define user/session cache partition, logout/expiry behavior, no unsent-loss warning bypass, conflict response and idempotency ledger. Test reload without network, storage denial and user switching in `tests/checklist-offline.test.mjs`.
5. **§9–13 delivery completeness:** Split the additive migration/manifest work and named tests by phase, including retention/legal hold and deletion from raw `source_events`, call transcripts, knowledge/evidence, provider storage and backup aging. Define a callable internal adapter for approval staging rather than implying a worker can directly invoke an MCP handler closure; preserve its grant/approval semantics and resumable dedupe. Add `tests/call-checklist-retention.test.mjs` and staging failure/crash cases. Rollback must explicitly stop existing capture when consent/feature requires it, expire prompts, and leave telephony/history usable.

## In-home consult

### Verified correct

- The MCP finding enum really disagrees with SQL/TypeScript (`mcp/estimating-tools.mjs:134`; `db/migrations/0010_estimating_records.sql`; `lib/estimating/types.ts`). Fixing this independently is justified; old aliases need preprocessing before enum validation.
- `applySiteFindings`, `loadLeadFacts`, `getSiteVisitPlan`, scope quantities and advisory workflow gates exist (`lib/estimating/scope.ts:63,214,329`; `lib/workflow/engine.ts:423–430`). This should extend the current estimating path.
- Floor reducer names and coordinate-based `addRoomRect`/`addOpening` are correctly identified (`lib/plan-ops.ts:88–110`). `measure-tools` is automation measurement, not tape capture.
- Local transcription currently decodes mono audio and uses `-nt` text output with a 120-second timeout (`lib/transcribe.ts:50–75`); timestamp/chunk extensions are genuinely needed. Independent complete recorder files are a reasonable proposal requiring Safari validation.
- 0073 is the next append-after-highest migration number: this tree ends at 0072. There is also an older 0067 gap; do not reuse it casually. The invoker guard exception is real (`deploy/db-roles.manifest.json:14`), so extending that existing function is not a new-trigger SECURITY DEFINER violation.

### Wrong or invented

- **Uncallable upload helper:** §12/§14 calls `persistBlob`, but it is private (`lib/upload-store.ts:110`, no export); public entry points are `storeUpload` and `storeBuffer`. Its DB insert uses module-global query, not the consult transaction.
- **Shared engine mismatch:** §9.2, plan lines 1459–1464, says `covered / missing / unclear`; discovery §5, lines 165–169, defines `open / partial / covered / not-applicable` and revisioned evidence. Consult SQL instead defines independent bigint segments without source/revision/supersession/shared-session linkage (lines 1834–1846). “Calls it as is” is false as specified.
- **Guards do not enforce stated authority:** §11.3 lines 1913–1922 allows agent INSERT with arbitrary `conducted_by`, edits to published definitions while status stays published, and changes to helpers/consent/review timestamps. Published definition bytes are not immutable. Protecting only a transition into reviewed does not protect an already-reviewed row from downgrade or evidence replacement.
- **Privacy promise contradicts implementation:** §8.1 says never shared outside SJ Carpentry; §8.3 sends text to Anthropic and includes audio in off-host B2 backups. “Audio never leaves the server” in D6/§8.3 is false even with local STT. Hiding an audio tag from Files also does not enforce assigned-staff-only audio access: the generic file route allows a projects-authorized user by file ID (`app/api/files/[id]/route.ts:20–42`).
- **Recovery/global serialization do not follow:** §9.1 lines 1410–1419 combines a process-local semaphore and per-chunk row claims, then claims two consults cannot transcribe concurrently. Two processes can claim different rows. Recovery only re-kicks `uploaded`, leaving crashes in `transcribing` stuck; its table has no lease timestamp/token. Next's `after.md:50` explicitly bounds work by route duration; a GET from an open device is not durable recovery.
- **Current-answer SQL permanently favors any review:** §11 view at lines 1785–1789 always sorts review ahead of later typed corrections. That can hide a legitimately reopened correction indefinitely. Ordering by adjusted device clock also does not detect causal concurrent edits or prove all other devices have finished syncing.
- **Finding application is not replacement/retraction:** §10.5 maps each measurement to existing quantity labels; `applySiteFindings` replaces one matching label (`lib/estimating/scope.ts:242–258`) and answers the first compatible plan item (`:306–315`). Multiple rooms/windows cannot each write the same label without overwriting each other; clearing/removing an answer does not retract old findings/quantities or reopen a plan item.

## Cross-plan

- **Migration numbering:** No actual collision now. Sub/discovery defer allocation; consult names 0073 with a merge-time renumber note. Allocate a single ordered implementation sequence when work starts; do not let independent PRs each take 0073. Check foreign-key dependencies for shared coverage before consult integration.
- **Tool/table collisions:** Proposed new tool names do not collide with current registrations in `mcp/*.mjs`; `record_site_findings`, document tools, `list_calls`/`get_call` are explicit extensions. `list_checklist_definitions` belongs to discovery; consult form version APIs remain distinct. Do not register a second `award_bid`. No sibling currently proposes the same new domain table.
- **Shared engine ownership:** Discovery owns states, schemas, segments/evidence, validation and engine lifecycle. Consult must consume its contract; its current alternative states and independent evidence IDs are incompatible. Consultation forms may remain separate definitions only with an explicit compiled-item mapping/version contract. Discovery's call-specific consent/nudge rules must not force owner-only consent or phone reminders onto staff consults.
- **Scope interface:** Agree on one versioned `consultScopeFacts` result shared by consult Phase 4 and sub Work Order drafting. Confirmed measurements and source photos are input evidence; sub price, client acceptance and Joe's release remain separate. Sub Phase 1/2 must not depend on consult Phase 4 to ship.
- **Privacy/operations:** The plans currently propose different consent and retention policies. They may use different durations, but must share truthful processor disclosures, legal-hold/deletion mechanics and access enforcement. Use one host-wide transcription budget and a worker scheduler that preserves immediate telephony and live queue latency. Do not run three independent unbounded background pipelines.
- **Validation conventions:** `package.json` runs the whole suite with concurrency four; the plans correctly avoid that on this box. Existing e-sign tests demonstrate isolated DB URLs and module-hook stubs (`tests/esign-lifecycle.test.mjs:1–70`). New DB tests must copy that explicit isolation/refusal pattern. No tests were executed because this is a read-only design review and the user forbids database access.
