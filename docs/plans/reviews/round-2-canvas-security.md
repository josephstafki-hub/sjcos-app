## Vulnerabilities / gaps

### High — saved-file MCP adapter reintroduces claimed-user authentication (§8.4)

The §5.2 transport guard is concretely scoped to the four Canvas tools and `canvasCall`. Section 8.4 separately introduces `/api/internal/canvas-files` for resolve/list/read/trash/restore, requiring a named principal reloaded from the DB but never specifying transport authentication for that principal. It routes existing bidding/upload tools through this adapter. Existing `principalPayload` and `internalCall` (`mcp/sjcos-mcp.mjs:195–228`) forward the HTTP caller's claimed identity while supplying the privileged internal secret. The HTTP handler accepts `x-sjc-principal-user`, run ID/profile/start headers (`:3146–3153`). Reloading that user proves the user exists, not that the caller is that user.

A holder of the external MCP token can claim Joe (or an authorized staff member), then invoke the ordinary project-file tools. Under the written adapter contract, the caller is neither unknown nor apparently unattended and can pass the saved-file resolver as the claimed person. This exposes even owner_only snapshots, and potentially permits trash/restore. No private source access or compromise of CRON_SECRET is needed. `mcp/bidding-tools.mjs:288–329, 403–420` confirms that the actual list/get paths are distinct from the four new Canvas tools. General statements that “MCP bypass” tests must pass do not define the missing enforcement mechanism.

### High — preselected owner sharing lacks a trustworthy sensitivity baseline and stale-confirmation protection (§§4.2, 5.1, 8.4, 9)

The staff full-permission union is explicit, but there is no equivalent conservative rule or server-maintained source-provenance mechanism for Joe's arbitrary page/diagram content. Tool input has model-supplied `required_areas` and optional project scope; no trusted source-record association establishes that a pasted invoice amount, earlier conversation financial context or owner shell-read data requires Money/Invoices. The real DAL represents owner permissions as `[]` and grants owner access implicitly (`lib/dal.ts:58–74`), so copying the stored owner permission array is not a safe fallback.

Example: Joe asks for a project-cost page; the model declares only projects (or no financial areas). The job reference derives projects, not money. The Save screen preselects Share with staff and presents that nonempty incomplete checklist. Normal Save then exposes costs to project-file readers lacking Money, without Joe deliberately removing a financial restriction. The empty-checklist warning does not cover this case. “Derived financial areas pre-ticked” is an intended result, but there is no normative derivation/fail-closed rule that produces it for this input. Decision 9 requires the default sharing selection, not silent declassification caused by omitted model labels.

There is also a concrete stale-dialog case: the dialog captures an earlier policy, another version expands the parent's required areas, and Save submits the old smaller staff set. The API re-derives current policy but permits Joe's submitted subset as an audited declassification. The request contains no expected policy revision or explicit downgrade acknowledgement bound to the newly removed areas. A routine click on a stale default can therefore become a reduction Joe never saw. Version pinning alone does not solve this because parent requirements cover every version.
