### New issues

- **S1 — Lifecycle and authority contradictions (§§10.1, 10.3, 10.5, 11).** `sub_agreements` permits `draft`, not `ready`, but §11.1 requires `ready` and `draft_hash` for either a version or agreement; the agreement table has no `draft_hash`. `uq_packet_live_agreement`/`uq_packet_live_scope` include declined packets (`state <> 'void'`), yet §10.3 returns a declined agreement to draft for a new packet. §10.5 both prohibits all narrow writes to `sub_scopes` and grants agent INSERT, with no function to create the parent needed by `draft_sub_scope`. The published lock order begins at `project_subs`, but §11.1 begins by locking the version/agreement; completion also needs to update an agreement described as locked FOR SHARE. These are implementation choices with competing answers, not wording nits.
- **S2 — Transaction/hash boundary (§§11, 14.2–14.3).** Real `lib/upload-store.ts:110–149` generates random file IDs, writes disk bytes and inserts via module-global `query`. Calling `storeBuffer` inside another transaction does not roll back its file row or bytes. A deterministic display name is not a uniqueness constraint. §11 needs an explicit storage checkpoint/orphan contract for unsigned PDFs and signature images as well as executed copies. The grant stores only the unsigned PDF `content_hash`; attachments are bound separately by `manifest_hash`, but the grant comparison does not include that hash. A replacement packet can retain identical unsigned bytes and change attachments while satisfying the described grant check. Also, restricting the final `sub_documents` copy does not classify unsigned PDFs/signature PNGs/attachments before execution: ordinary projects-area file reads remain possible through `app/api/files/[id]/route.ts` unless those files are explicitly restricted too.
- **S3 — Relational and gate bypasses (§§10.1–10.2, 12).** `sub_scopes.current_version_id` can reference another scope's version; a version's agreement can belong to another sub; packet sub/project/draft can disagree with its agreement/version; PO `scope_version_id` is similarly unscoped. There is no stated composite validation covering these relationships. The PO guard is UPDATE OF status only, and start confirmation is UPDATE only: owner/application inserts already queued/sent or already confirmed bypass them. Existing `purchase_orders` really supports queued/sent (`db/schema.sql:2817`), so this is a concrete transition gap. Schedule insertion is covered correctly.
- **S4 — Exact interfaces remain unfinished (§§7.1, 14.1).** `record_sub_change_request.kind` is only `enum`, and update `lines`, `exclusions`, `allowances`, `site_rules` have no complete validation schema. §7.1's source fields exceed the actual consult export (C3). The revision log's claim of exact schemas therefore overstates the text.
- **S5 — Lost repairs (§17.4).** Real `lib/reminders.ts:33–39` inserts the dedupe key separately from notification delivery. Crash after claiming `subpkt:<id>:stuck` but before creating its repair to-do permanently suppresses that repair on later daily scans. “Claims are atomic” prevents duplicates but does not ensure delivery.

### New issues

- **D1 — Hangup is outside the independent lane (§10.1).** The live loop claims only `call.transcription`; the main loop excludes only those events. A durable `call.hangup` can therefore wait behind the deliberately slow recording/notes job. The immediate webhook path can usually update the call, but `app/api/voice/webhook/route.ts:18–29` explicitly relies on worker replay if the process dies before `after()` runs. A restart in that window leaves the live loop able to remind against stale live state until the main queue drains. The proposed slow-job test does not inject that case. Also specify how two live-loop pool slots accommodate the dedicated LISTEN client, advisory-lock/model lifetime and concurrent control/heartbeat work without starving the latter.
- **D2 — The promised shared adapter cannot publish its instances (§§8.2–8.5).** Discovery publishes one immutable coverage version in the form-publication transaction. Consult §9.2 derives item IDs from form checksum **and runtime instance UUID**, then creates repeatable rooms/windows after publication. Those item IDs cannot be members of the already-published version. Discovery's stable item UUID across wording changes also differs from checksum-derived identity. `Evidence.timing_basis` is required here and missing from consult's claimed exact evidence shape; `source_event_id='<consult>:<chunk_seq>:<idx>'` differs from consult's `provider_event_id='chunk UUID:ordinal'`. The discovery key also needs device identity when helpers have independent chunk sequences.
- **D3 — Incomplete security/apply contract (§8).** §8.4 grants raw SELECT on all shared sessions, segments, coverage and events to agent/worker/readonly. Consult §11.3 explicitly prohibits those broad reads. A consult-local wrapper cannot revoke that shared-table bypass. `checklist_start_session`/manual writes take caller-supplied actor fields without the signed scope context consult requires. Separately, `EngineOutput.base_revision` has no corresponding session revision in `EngineInput`; the revision snapshot the runner must pin and check is undefined. Apply's “only suggest accepted” in consult/unknown-speaker mode conflicts with the permitted correction `downgrade`/`clear_suggestion` operations; define which maintenance changes remain legal. `prior_record` rows called never re-judged in §8.5 lack an explicit manual-lock rule.
- **D4 — Retention is not shared or complete (§14).** Discovery keeps audio and text until 180 days after signed contract/lost status; consult keeps audio 90 days and text 180 days from capture end. Discovery's recoverable trash on request contradicts consult's permanent active-store purge. Active never-contracted linked leads have no bounded start clock. `checklist_clear_segments` only strips coverage/suggestion quotes: `checklist_events.before/after`, original call transcript fields, generated draft/summary/knowledge copies and restored backups need explicit targets and access revocation. The summary-note exception cannot preserve transcript quotations accidentally. Holds are session-level here versus a separate scoped consult hold ledger.
