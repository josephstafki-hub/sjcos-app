## Wrong or invented

**The Phase-0-only release is not dependency-complete for deletion/recovery.** H5 and §§8.1/10 explicitly allow Browser access after **0105 privacy acceptance**, independently of the Canvas renderer. Phase 0's build list is Browser 0100 plus Canvas 0105 (§10 lines 696–706). At the same time, §8.1 line 527 unconditionally changes `deleteConversationAction` to the §8.5 command. That command requires journal fences on every private read/write, synchronous independent intent/high-water durability, startup replay and resumable maintenance. Its lease/checkpoint table `ask_canvas_maintenance` is allocated to **0106 / Phase 1** (§8.1 lines 510–511; §8.2 line 544); its recovery/loss-of-primary tests are likewise only in the Phase-1 `canvas-retention-db` list. Phase 0 neither brings those prerequisites forward nor explicitly disables deletion until they exist.

A builder following the stated phase exits can therefore release Browser/private threads while thread Delete calls later-phase infrastructure, or implement an interim DB-only tombstone that violates the unconditional §8.5 acknowledgement/restore contract. Keeping Canvas renderer flags off does not gate the existing thread-delete action or private-thread startup. This is a release-order ambiguity affecting working deletion and recovery, not a request for another retention policy or a different journal architecture.
