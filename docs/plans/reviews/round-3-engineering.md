### New issues

- **S6 — Paper import cannot satisfy the electronic packet contract (§17 Phase 1 versus §§10–11).** Phase 0 deliberately produces paper signatures/scans. Phase 1 promises to import those scans as `executed`, using `sub_channel='in_person'`, witness Joe and an “Imported from paper” flag. But the schema has no paper-evidence discriminator/import fields. Every packet requires a separate unsigned file, owner signature file and owner timestamp; executed packets additionally require sub signature and initials files. The artifact guards require those slots to contain their matching roles; §11's only completion path starts from electronically captured `sub_signed` evidence. A scan alone cannot traverse that path. Calling it `in_person` describes the existing electronic iPad path and does not define an alternate validation contract. An implementer must either reject the promised imports, invent electronic consent/signature artifacts, or weaken mandatory guards. This also leaves adoption/readiness and the promised retention of imported evidence undefined.

### Required to reach 10

1. Define one owner-only paper-import evidence path compatible with the tables, artifact roles and guards: distinguish original paper signing from electronic capture; specify scan/hash, actual signer/date evidence, importing owner/time and witness provenance; state how the imported agreement/scope becomes signed/current and contributes to readiness without fabricating electronic consent or signature PNGs. Alternatively explicitly keep scans as legacy reference-only documents and revise Phase 1/adoption promises accordingly. Add paper master and scope import, duplicate/crash retry, invalid/missing evidence, narrow-login denial and readiness/current-pointer cases to the named lifecycle/access suites. This is required because the advertised scan-only import cannot populate the required electronic evidence structure as written.

- **C4 — Measurement suggestions cannot use the specified evidence-reference table (§§9.2–9.3/11.1 versus discovery §8.3).** The consult table contract explicitly requires `consult_suggestions.evidence` to have `checklist_evidence_refs` rows, including the independent dimension/count extraction in §9.3. That shared table requires a runtime checklist `item_id`; its primary key is `(session_id,item_id,slot,ordinal)` and its only slots are `committed|suggested`. Measurement proposals instead address `(instance_id,field_key)`, have their own suggestion UUID, and deliberately sit outside checklist items (discovery §8.5: dimensions/photos remain deterministic form data). A window-width proposal therefore has no valid item FK. Assigning it to an unrelated question item would both misattribute lineage and collide with that item's coverage suggestion at ordinal 0; two independent field proposals cannot be distinguished either. Sharing the Evidence value schema does not make this checklist-specific relational owner usable for field suggestions.
