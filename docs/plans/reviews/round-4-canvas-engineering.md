## Wrong or invented

**The new description of the staff input surface is narrower than the actual runtime, and the proposed provenance gate does not yet close that difference.** Canvas §5.1 calls the profile “sjcos + read-only operating docs” with “repo tools excluded”; §9 then says operating-doc reads are recorded and question plumbing adds no data areas. `lib/authority/run-profile.mjs:17–35,77–95` actually leaves native **Read/Glob/Grep** available. A scratch cwd and docs `--add-dir` are not a provenance gate for their results. `mcp/interact-mcp.mjs:50–64,108–110` also auto-allows those tool names without checking paths. The present runner observes tool events after emission and `onToolUse` at `scripts/run-claude-agent.mjs:473–480` ignores every non-sjcos tool; its telemetry is not a synchronous before-delivery interlock.

This is directly relevant to supported inputs: `lib/actions/ai-chat.ts:223–228` gives Claude absolute attachment paths to read with its native tool, and the runner does the same for earlier attachments at `:297–300`. Thus even recording an attachment envelope at send time does not itself establish which bytes a later native read delivered, prevent an untracked path/read, or serialize its pending/completion against a Canvas commit. §9 specifies the desired outcome, but only the sjcos wrapper has a named before-result enforcement mechanism. Observing stdout and eventually writing a row cannot guarantee the CLI has not already consumed a native result and called `show_canvas` in its other MCP process.

There is a second input on that same outside-wrapper boundary: both servers register `ask_owner` (`mcp/sjcos-mcp.mjs:2978`; `mcp/interact-mcp.mjs` at its final registration). `mcp/interact-tools.mjs:45–55,100–116` returns arbitrary typed `other` text from `agent_interactions.response` directly as a tool result. It does not flow through `sendMessageAction` or the runner's steer ingestion. The sentence that replies use prompt-ingestion accounting must therefore become an explicit integration in this shared completion path, including the interact instance; treating the whole question channel as zero-area plumbing is unsafe. No new Canvas tools in interact are needed.

Without a chosen synchronous mechanism for these paths, a builder can either incorrectly mark such a chat complete or conservatively refuse normal staff Canvas after these supported interactions. The generic native-doc/file-ingestion test labels in §10 do not establish that mechanism or prove the race closed. This finding does not reopen the already specified full-C/unknown policy, demand a model classifier, or require exhaustive registry contents to be printed in the plan.
